# Provisional decisions

Dated 2026-09-29, extended through 2026-10-02. Sections below the source-integration entries are history: where a row names `tprims-blas`, `tprims-linalg`, `tprims-core`, `tprims-bundle`, engines, `private-gemm-x86`, the `tensorprimitives/` tree or an environment variable, read the source-integration section above for the current rule. ## 2026-10-01 TAPP C API and executor ownership ([#26](https://github.com/tensor4all/tprims-rs/issues/26))

Superseded in part by #37: the C ABI is the single crate `tprims-capi`; the BLAS C symbols are gone, and products run through `Plan::execute_raw` with `Exec`.

| Question | Ruling | Evidence or next check |
| --- | --- | --- |
| Contraction C ABI: a tprims-specific plan API or TAPP? | **Decided:** the standard TAPP interface, with the prototypes of the pinned upstream headers (`TAPPorg/reference-implementation@77c32d744ee6`, vendored verbatim under `crates/tprims-capi/include/`), implemented in `tprims-capi` over `tprims_contract::Plan`. The proprietary `tprims_contract_plan_*` ABI was removed (the ABI is not stable and no downstream compatibility need was identified). DLPack operands remain for the tprims extension headers. | Tests: `tprims-capi/tests/c_abi.rs` (a C and a C++ program that include only the pinned headers) and the TAPP conformance, rejection, aliasing, executor and layout tests in `tprims-capi/tests/`. |
| Who owns a C host's Rayon pool? | **Decided:** the C host owns the executor and the executor owns the pool; both are created and destroyed through the C API. `TAPP_create_executor` and executor `0` are serial; `tprims_tapp_executor_create_rayon` creates the owned pool (`nthreads == 1` is serial with no workers, `0` is an error, width never inferred from the environment); `TAPP_destroy_executor` stops and joins it (BUSY with calls in flight, WOULD_DEADLOCK from its own worker, handle left live; a failed creation joins what it started). No retain/release, no separate close, no reaper thread, no public pool handle. Rust hosts keep borrowing their pool. | `tprims-core` unit and integration tests (TLS-teardown handshake, failed creation with an injected spawn failure). |
| One executor and one error table across parts? | **Decided:** every call takes a `TAPP_executor`; a `TAPP_error` is a `tprims_status`. `tprims-capi` owns the executor, the codes (two added: `LABELS`, `UNSUPPORTED`; `CLOSED` retired) and `TAPP_check_success` / `TAPP_explain_error`. The `TAPP_ERROR_*` numbers are provider-defined in TAPP, so within the standard. | `tapp_abi_layout.rs` pins the values. |
| How does a TAPP product pick its width? | **Decided:** through `Exec`, never serially by accident: the width is chosen at each call from the plan's work estimate and the executor's budget (see the contract consolidation table below). Small work stays on the caller of a larger pool; a nested call from a worker falls back to serial. | `tprims-capi/tests/tapp_executor.rs`, `tapp_pool_sharing.rs`. |
| Aliasing rules of a product? | **Decided:** `D` must not overlap `A` or `B`; `C == D` is an in-place update only when `C` maps every element as `D` does after matching labels; any other overlap of `C` and `D` (judged on addressed byte ranges, conservatively) is rejected; a `D` that overlaps itself is rejected at plan creation; the checks do not depend on `beta`. A null `C` with a nonzero `beta` is `UNSUPPORTED` (the meaning of `TAPP_IN_PLACE` is an open TODO upstream). Batches validate every item with the same code before writing anything. | `tprims-capi/tests/tapp_aliasing.rs`. |
| Precision and element operations? | **Decided:** `TAPP_DEFAULT_PREC` and the storage precision are accepted; any other precision, and any element operation other than identity or conjugation, is `UNSUPPORTED` instead of being ignored. `op_D` conjugates the whole result `alpha*A*B + beta*op_C(C)`, as the upstream reference does. | `conformance.rs`, `aliasing.rs`. |
| Overhead of the new C ABI against the old one? | **Open (deferred in this change):** `benchmarks/c/bench.c` is migrated to TAPP and smoke-run only; the paired 1T/4T measurement with the A/A noise floor, and the 4T throughput check, are not run, and no speedup or overhead is claimed. The 2026-09-30 table in [the C benchmark](../benchmarks/c/README.md) is of the removed API. | Run `benchmarks/c/run.sh` on an idle EPYC with predeclared thresholds. |

## 2026-10-01 opt-in DynamicTiles scheduling (issue #29)

Current form: `Partition::DynamicTiles { job_m, job_n }` in `PlanConfig`.

| Question | Ruling | Evidence or next check |
| --- | --- | --- |
| Scheduler shape? | **Decided:** one epoch per (batch, NC panel, KC slab): cooperative B packing, publication barrier, atomic claiming of row bands (2-D band x column-subtile jobs when bands < workers), completion barrier taken by every worker. One monotonic claim counter per epoch, owned by the invocation; no deques, no split-K, no atomic accumulation. Width 1 never enters it. | `tprims-contract/src/driver/dynamic.rs`, `driver/tests/dynamic.rs` |
| Arithmetic? | **Shared with the static path** (`compute_block`), so dynamic is bitwise identical to static/serial at a fixed blocking. Direct-B takes the same two barriers (counter reset and cross-K ordering still need them) and allocates no B panel: an explicit tradeoff against the static barrier-free direct-B split. | `tests/dynamic.rs` |
| Configuration? | **Decided:** `PlanConfig::partition` (`Partition::DynamicTiles { job_m, job_n }`); a non-default policy is a requirement of the packed driver and forces it (never ignored). `DynamicTiles + align_c_lines` is not expressible. Job extents are logical multiples of the selected family's MR/NR (so valid extents differ per family). | `tprims-contract/src/driver/tests/dynamic.rs` |
| Performance? | **Deferred (maintainer decision).** The Stage-0 need measurement and the paired 1T/4T static-vs-dynamic suite with A/A noise were skipped; opt-in only, no default change, no speed claim. `--partition dynamic:JM,JN` in `benchmarks/` (blas, contract) makes the later comparison runnable with separately labelled rows. | `benchmarks/src/partition.rs` |

## Structure and ABI

The 2026-10-02 source-integration section is current: one `tprims-capi` crate builds `libtprims`; there is no per-part C ABI crate and no feature-selected bundle, and the kernel crate is `tprims-kernel`.

| Question | Present position | Evidence or next check |
| --- | --- | --- |
| Facade crate? | **Decided: no facade.** Every part is an independently usable crate, as in tenferro-rs. | Maintainer decision, 2026-09-29 |
| Crate naming? | **Decided:** `tprims-<part>` with a short descriptive part name (`tprims-exec`, `tprims-kernel`, `tprims-contract`, `tprims-capi`). Crate, header and C symbol map one to one. Existing `strided-*` crates keep their names. No `tensor4all` or `t4a` naming: the stack targets hosts beyond tensor4all, and `t4a_` is already the tensor4all-rs C prefix. | Maintainer decision, 2026-09-29; `tprims` unused on crates.io at that date |
| `contract` or `tensordot`? | **Decided: `tprims-contract`.** NumPy / PyTorch / JAX `tensordot` has no batch indices; this operation does, as in cuTENSOR `cutensorContract`. | [cuTENSOR API](https://docs.nvidia.com/cuda/cutensor/latest/api/cutensor.html) |
| Where does the C ABI live? | **Decided (revised by #37):** one crate, `tprims-capi`, builds `libtprims` (`cdylib`, `staticlib`, `rlib`); the earlier plan of per-part `rlib` ABI crates linked by a feature-selected bundle was dropped when BLAS and linalg were removed and only the contraction ABI remained. | Source-integration section above; `cargo tree`. |
| Separate shared library per part? | Rejected. Handles, Rayon runtimes and (for static libraries) Rust std symbols would be duplicated. | Design reasoning; see [architecture](architecture.md#one-shared-library) |
| Data exchange? | **Decided: DLPack.** Operands are a borrowed `tprims_tensor` (`DLTensor*` view plus DLPack flags), built from a `DLManagedTensorVersioned` without taking ownership or from a raw `DLTensor` with caller-supplied flags; read-only outputs rejected before any write. Library-allocated outputs as `DLManagedTensorVersioned`. Conjugation as a per-operand argument. No hidden materialization. | [DLPack header](https://github.com/dmlc/dlpack/blob/main/include/dlpack/dlpack.h): the READ_ONLY flag lives in `DLManagedTensorVersioned.flags`, so a bare `DLTensor*` cannot carry it ([#2](https://github.com/tensor4all/tprims-rs/issues/2)) |

| `f16` / `bf16` in ABI v1? | Open. DLPack has the tags; kernels do not exist yet. | Decide before the first ABI release |
| Repository placement of `tprims-exec`? | **Decided: monorepo.** strided-rs, tensorprimitives-rs and the benchmark suite were imported here with history (Phase 0); `tprims-exec` lives in `crates/`. No repository-level cycle remains. | Maintainer decision, 2026-09-29 |
| strided-rs source location? | **Decided (revised 2026-09-30):** an external dependency on tensor4all/strided-rs, pinned to the v0.4.4 commit exactly as tenferro-rs pins it, so both share one `StridedView` (since #37's elementwise follow-up: a post-v0.4.4 main commit carrying strided-rs#283's in-place update ops and #285's blocked transposed mul; tenferro-rs's pin must follow). strided-rs itself removed its facade and einsum crates (strided-rs #282); strided benchmarks live in strided-rs-benchmark-suite. | Benchmark suite? | **Decided:** imported under `benchmarks/` as `tprims-bench`; the einsum half is frozen. Every Phase 1 implementation adds rows measured at 1T and 4T in the same run. | Maintainer decision, 2026-09-29 |
| Iterative Krylov solvers? | **Deferred, out of scope.** They need a linear-operator callback, convergence control and preconditioning, a different contract from tensor contraction, and many consumers carry their own. | Maintainer decision, 2026-09-29 |

## Execution

The C-ABI crate in the rows below is now `tprims-capi`; the BLAS and dense-linear-algebra providers are gone, and faer remains an internal strategy of `tprims-contract` in Phase 1.

| Question | Present position | Evidence or next check |
| --- | --- | --- |
| How much pool-entry cost is acceptable? | **Decided:** about 10 µs per parallel kernel is acceptable. Serial operations never enter a pool; they run on the calling thread. Parallel width is chosen from the amount of work, so full-width fan-out is reserved for large kernels. | [Rayon entry measurement](../experiments/rayon-entry/README.md), 2026-09-29, M5 Max: `install` 4 to 10 µs at 1 to 4 threads; 18-thread fan-out 55 to 200 µs. Maintainer decision, 2026-09-29. |
| Who owns the pool when a host library such as tenferro-rs also uses Rayon? | **Decided: borrow.** `tprims-exec` borrows the host's pool for the duration of a call (or a host session) and never creates a second pool beside it. `tprims_exec_rayon_create` exists only for C hosts that have no pool. **Superseded (2026-10-01):** the C host now creates it through `tprims_tapp_executor_create_rayon` and destroys it through `TAPP_destroy_executor`. | Two pools would oversubscribe cores and turn every call into a cross-pool handoff. Sharing a pool by reference requires one Rayon build in one binary. |
| Where is the pool entered? | **Decided:** inside a kernel, and only when it runs in parallel. If the calling thread is already a worker of the borrowed pool, the kernel runs in place without `install`. The caller's thread stays the driving thread for everything else, so host thread-local state needs no propagation. | Contrast: tenferro enters once per session and runs the whole session on a worker ([tenferro #1945](https://github.com/tensor4all/tenferro-rs/issues/1945)). |
| Initial backend? | **Decided (provisional):** faer for GEMM and dense linear algebra. `Par::Seq` on the calling thread for serial work; `install` on the borrowed pool, then `Par::rayon(n)`, for parallel work. Replace kernels only with measured justification. | Works with faer's ambient-pool API ([faer #319](https://codeberg.org/sarah-quinones/faer/issues/319) still open) because entry happens only at parallel kernels. |
| C ABI for execution: explicit handle per call, or a C-level "enter pool and run callback" command? | **Decided (Phase 1f; type renamed 2026-10-01 to `TAPP_executor`): explicit executor on every call**, kernel-level entry inside; small calls never enter the pool from C either. Pools created from C are owned (`Pool::owned`) and closed synchronously (workers joined, TLS-destructor handshake test). The C boundary currently costs 300-450 ns per small call (3x Rust for an 8x8 GEMM); removing per-operand metadata allocations is the follow-up. | [C ABI bench](../benchmarks/c/README.md), EPYC 7713P, `509f30f` |
| `tprims-exec` shape (Phase 1a)? | **Implemented (provisional):** `Pool<'p>` wraps a borrowed `&rayon::ThreadPool` with an SPMD mutex and entry counters; `Exec::{Serial, Rayon { pool, budget }}` with `install(k, op)` (faer-style, width one inline), `for_each_partition(k, f)` (barrier-free) and `broadcast(width, f)` (SPMD, full pool, serialized, refused when nested or wider than the pool). ## 2026-10-02: contract consolidation (source integration PR 3)

| Question | Decision |
| --- | --- |
| One description of a contraction? | **Decided:** a validated `Problem` (original layouts, normalized M/N/K/H role axes with signed A/B/C/D strides, C mode, checked spans) with `Labels` and `DotGeneral` as two front ends of one lowering. `Plan<T>::new(&Problem, &PlanConfig)` replaces `ContractPlan`, the old labels-based driver plan and the traits crate's `Problem`. |
| Strategy choice? | **Decided:** by rule, in order: an explicit kernel, selector, partition, complex method, blocking, cache model or write-back request forces the packed driver; else an all-batch problem is elementwise; else a copy-free full-semantics fusion runs on faer; else packed. The old `Strategy`/`Flags`/`EngineChoice` are gone. |
| faer applicability? | **Decided (amended by Phase 2 W2, 2026-10-03):** faer only for fusions that copy no operand and implement the full update: `op_D` is distributed over the sum by conjugation flipping; the previous-D term and a separately described C are written into D by one parallel output-sized strided pass (`D = op_D(beta*op_C(C))`, strided-basic) before faer accumulates the product. That pass is not operand materialization (A, B, C are never copied or packed; `no_materialize` and `PlanReport::materialized` are unchanged). A separate C goes to faer only when K >= 512 or the output has at most 2^20 elements; a large output with a small K stays packed (the pass costs 20-50% of faer there, measured). A reduction one input lacks stays on packed. The old copying branches are deleted. | [W2 results](../benchmarks/benchmarks/tprims/contract/results/2026-10-03-phase2-w2/decision.txt) |
| Elementwise semantics? | **Decided:** one strided pass (since #37 follow-up: strided-basic kernels with `op_D` folded into the other conjugations and one dispatch per execution, not a hand-rolled odometer loop with per-element flags; in-place accumulation uses strided-rs's `execution` traversal with a local raw-pointer inner loop, because a checked call would need a second view aliasing the `&mut` destination) with the full `op_D(alpha*op_A*op_B + beta*op_C(C))`, `C` in place, separate or absent; it also serves `alpha == 0` and an empty contraction for every strategy, so `op_D(beta*op_C(C))` is computed identically everywhere and reads no input. |
| Explicit kernel or partition on an all-batch problem? | **Decided (behaviour change):** runs the packed driver. The baseline refused it with `EngineUnsupported`. Tested for `StaticGrid` and `DynamicTiles`. |
| `Partition`? | **Decided:** `StaticGrid { pin, align_c_lines } \| DynamicTiles { job_m, job_n }`; `None` is the default rule. `PartitionMode` is gone (`Rows`, `Cols` and the ungated `Rule` had no retained consumer); `DynamicTiles` + `align_c_lines` is unrepresentable. |
| Selector context? | **Decided:** no thread budget and no candidate grids: a plan is built before an executor is chosen and never reselects for another budget. Operand labels are gone (the problem is label-free after lowering). |
| Width? | **Decided:** chosen at each call from `2 * macs * (4 if complex) * NS_PER_FLOP` and the executor's budget; one `NS_PER_FLOP` (0.05, provisional) replaces the three copies. |
| `contract_batched` schedule? | **Decided:** items at least as many as the width are partitioned over it, each serial; fewer items run one after another, each on the whole `Exec`. All items are validated before any runs. |
| Raw (C) execution? | **Decided:** `Plan::check_raw` is the pointer-only semantic preflight (output overlap, `C`/`D` aliasing, judged on address ranges); null pointers stay the adapter's. TAPP lowers once and keeps its sequential item loop. |
| Legacy `KernelSet`? | **Decided:** deleted. The planner resolves families from the registry; the default menu is the registry's built-in families of the preferred ISA and scheme, and a test pins that it equals the old dispatch menu entry for entry. |
| Benchmarks? | **Decided:** `tcbench` keeps `run`, `verify`, `info`, `--stress`; `sweep`/`shapes`/`orient`/`premise` are deleted. The three complex methods are a knob, not three engines. GEMM corpora are contraction cases. No timing was run for this PR. |
| All-batch problems after Phase 2? | **Decided by the maintainer, 2026-10-02**, after the per-element-branch defect in the hand-rolled elementwise loop (runtime flags per element, no contiguous inner loop): contractions with a K role use only the packed driver; all-batch (pure elementwise) problems are delegated to strided-rs permanently, with `op_D` folded into the other conjugations and monomorphized flag-free bodies. They are not removed in Phase 2. Shared rules: tensor4all-agent-rules#16 (no runtime mode flags in tensor-sized loops; elementwise work via strided-rs; structural review of inner loops). | Spec D5, section 4.3 rule 2, section 10 |
