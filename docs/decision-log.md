## 2026-10-01 TAPP C API and executor ownership ([#26](https://github.com/tensor4all/tprims-rs/issues/26))

| Question | Ruling | Evidence or next check |
| --- | --- | --- |
| Contraction C ABI: a tprims-specific plan API or TAPP? | **Decided:** the standard TAPP interface, with the prototypes of the pinned upstream headers (`TAPPorg/reference-implementation@77c32d744ee6`, vendored verbatim under `crates/tprims-core/include/`), implemented by the imported `tensorprimitives-tapp` as an `rlib` of the bundle (feature `tapp`) over `tensorcontract::Plan`. The proprietary `tprims_contract_plan_*` ABI and `tprims-contract-capi` are removed (the ABI is not stable and no downstream compatibility need was identified). The Rust `tprims-contract::ContractPlan` and its permute-plus-GEMM path stay; offering them through TAPP is separate work. BLAS keeps DLPack operands. | Tests: `tprims-bundle/tests/c_abi.rs` (a C and a C++ program that include only the pinned headers), `tensorprimitives-tapp/tests/` (cases 1 to 4, output order, conjugation, C/D, negative strides, scalars, `beta == 0`, rejections). |
| Who owns a C host's Rayon pool? | **Decided:** the C host owns the executor and the executor owns the pool; both are created and destroyed through the C API. `TAPP_create_executor` and executor `0` are serial; `tprims_tapp_executor_create_rayon` creates the owned pool (`nthreads == 1` is serial with no workers, `0` is an error, width never inferred from the environment); `TAPP_destroy_executor` stops and joins it (BUSY with calls in flight, WOULD_DEADLOCK from its own worker, handle left live; a failed creation joins what it started). No retain/release, no separate close, no reaper thread, no public pool handle. Rust hosts keep borrowing their pool. | `tprims-core` unit and integration tests (TLS-teardown handshake, failed creation with an injected spawn failure). |
| One executor and one error table across parts? | **Decided:** BLAS and TAPP take the same `TAPP_executor`; a `TAPP_error` is a `tprims_status`. `tprims-core` owns the executor, the codes (two added: `LABELS`, `UNSUPPORTED`; `CLOSED` retired) and `TAPP_check_success` / `TAPP_explain_error`. The tensorprimitives-tapp `TAPP_ERROR_*` numbers changed to match (provider-defined in TAPP, so within the standard). | `abi_layout.rs` pins the new values. |
| How does a TAPP product pick its width? | **Decided:** through the `Spmd` seam on the executor (`Plan::run_raw_with`), never `Plan::run_raw`: width is `Exec::width_for` of the plan's flops with the same provisional 20 GFLOP/s and `WidthPolicy` that `tprims-blas` and `tprims-contract` use, capped by the budget snapshotted at the call. Small work stays on the caller of a larger pool; a nested call from a worker falls back to serial. No kernel threshold or provider selection changed. | `tensorprimitives-tapp/tests/executor.rs`, `pool_sharing.rs`. |
| Aliasing rules of a product? | **Decided:** `D` must not overlap `A` or `B`; `C == D` is an in-place update only when `C` maps every element as `D` does after matching labels; any other overlap of `C` and `D` (judged on addressed byte ranges, conservatively) is rejected; a `D` that overlaps itself is rejected at plan creation; the checks do not depend on `beta`. A null `C` with a nonzero `beta` is `UNSUPPORTED` (the meaning of `TAPP_IN_PLACE` is an open TODO upstream). Batches validate every item with the same code before writing anything. | `tensorprimitives-tapp/tests/aliasing.rs`. |
| Precision and element operations? | **Decided:** `TAPP_DEFAULT_PREC` and the storage precision are accepted; any other precision, and any element operation other than identity or conjugation, is `UNSUPPORTED` instead of being ignored. `op_D` conjugates the whole result `alpha*A*B + beta*op_C(C)`, as the upstream reference does. | `conformance.rs`, `aliasing.rs`. |
| Overhead of the new C ABI against the old one? | **Open (deferred in this change):** `benchmarks/c/bench.c` is migrated to TAPP and smoke-run only; the paired 1T/4T measurement with the A/A noise floor, and the 4T throughput check, are not run, and no speedup or overhead is claimed. The 2026-09-30 table in [the C benchmark](../benchmarks/c/README.md) is of the removed API. | Run `benchmarks/c/run.sh` on an idle EPYC with predeclared thresholds. |

## 2026-10-01 neutral contraction interface (#31)

| Question | Ruling | Evidence or next check |
| --- | --- | --- |
| Where does the whole-backend boundary live? | **Decided:** a new `tprims-contract-traits` crate (depends only on `strided-view` and `thiserror`) owns `DotGeneral`, `Shape`, `Layout`, `Problem`, the canonical `validate_layouts`, the shared `Error`, `ContractionBackend<T>`, `PreparedContraction<T>` and `HostExecution`. `tprims-contract` re-exports `DotGeneral`, `Shape`, `Error`, `Result` unchanged and implements the traits as `TprimsBackend`; `ContractPlan<T>` stays the concrete type. | `crates/tprims-contract-traits/tests/dependency_direction.rs` (cargo tree) |
| Host-execution callbacks (the open API detail)? | **Decided:** `HostExecution` is object safe and carries `budget`, `install(k, &mut dyn FnMut(Par) + Send)`, barrier-free `for_each_partition(k, &dyn Fn(usize) + Sync)` and co-scheduled `broadcast(width, ..) -> Result<(), HostError>` (all-or-nothing; `Unavailable` for serial/nested). These mirror `Exec::install`, `for_each_partition` and `broadcast`, so `tprims-exec` and `tprims-core` signatures did not change: the adapter `tprims_contract::ExecHost` (outside the trait crate) implements the trait over `Exec`. No `KernelFamily`, packing buffer or `width_for` cost model in the trait. A tprims plan needs the pool's workspace, so `ExecHost` implements the `unsafe trait NativeHost` and answers `native(TypeId)` with its own address and `tprims-contract` recovers the `Exec` from it (the hook is the `unsafe trait NativeHost`, reached through the safe `HostExecution::native_host`, so a safe host cannot forge a pointer); any other host is served only at budget one (calling thread, no workspace) and otherwise fails with `HostError::MissingCapability` before writing. | `crates/tprims-contract/tests/neutral_interface.rs` (foreign host, 1T no pool entry, 4T, nested, concurrent) |
| Errors? | **Decided:** one `Error` type for both layers (no conversion); `Backend` now holds `Box<dyn Error + Send + Sync>` so lower-layer errors stay downcastable. `Error` is no longer `Clone`/`PartialEq` (providers' errors cannot be required to be). Preparation-time refusals (`WouldMaterialize`, `Unsupported`, missing host capability) report `is_unsupported()`, i.e. nothing was written. The permute+GEMM-with-named-kernel refusal moved from `Backend` to `Unsupported`. | `crates/tprims-contract-traits/tests/interface.rs` |
| Overhead evidence? | **Partial.** Allocation count and bytes through the trait equal the concrete path exactly (serial, both strategies; the permute+GEMM copy is the plan's own and identical). The paired 1T/4T concrete-vs-trait timing is deferred. | `crates/tprims-contract/tests/neutral_alloc.rs` |

## 2026-10-01 opt-in DynamicTiles scheduling (issue #29)

| Question | Ruling | Evidence or next check |
| --- | --- | --- |
| Scheduler shape? | **Decided:** one epoch per (batch, NC panel, KC slab): cooperative B packing, publication barrier, atomic claiming of row bands (2-D band x column-subtile jobs when bands < workers), completion barrier taken by every worker. One monotonic claim counter per epoch, owned by the invocation; no deques, no split-K, no atomic accumulation. Width 1 never enters it. | `tensorcontract/src/driver/dynamic.rs`, `tests/dynamic.rs` |
| Arithmetic? | **Shared with the static path** (`compute_block`), so dynamic is bitwise identical to static/serial at a fixed blocking. Direct-B takes the same two barriers (counter reset and cross-K ordering still need them) and allocates no B panel: an explicit tradeoff against the static barrier-free direct-B split. | `tests/dynamic.rs` |
| Configuration? | **Decided:** `GemmConfig::{partition, partition_opts}` and `Plan::with_partition`; a non-default policy is a requirement of the packed driver and is refused (never ignored) by faer / `private-gemm-x86`, the faer-loop batched strategies, grouped GEMM, permute+GEMM and the elementwise pass. `DynamicTiles + align_c_lines` is rejected. Job extents are logical multiples of the selected family's MR/NR (so valid extents differ per family). | `tprims-blas/tests/dynamic_partition.rs`, `tprims-contract/tests/dynamic_partition.rs` |
| Performance? | **Deferred (maintainer decision).** The Stage-0 need measurement and the paired 1T/4T static-vs-dynamic suite with A/A noise were skipped; opt-in only, no default change, no speed claim. `--partition dynamic:JM,JN` in `benchmarks/` (blas, contract) makes the later comparison runnable with separately labelled rows. | `benchmarks/src/partition.rs` |

## Structure and ABI

| Question | Present position | Evidence or next check |
| --- | --- | --- |
| Facade crate? | **Decided: no facade.** Every part is an independently usable crate, as in tenferro-rs. | Maintainer decision, 2026-09-29 |
| Crate naming? | **Decided:** `tprims-<part>` with a short descriptive part name (`tprims-exec`, `tprims-gemm-kernel`, `tprims-blas`, `tprims-linalg`, `tprims-contract`). Crate, header and C symbol map one to one. Existing `strided-*` crates keep their names. No `tensor4all` or `t4a` naming: the stack targets hosts beyond tensor4all, and `t4a_` is already the tensor4all-rs C prefix. | Maintainer decision, 2026-09-29; `tprims` unused on crates.io at that date |
| `contract` or `tensordot`? | **Decided: `tprims-contract`.** NumPy / PyTorch / JAX `tensordot` has no batch indices; this operation does, as in cuTENSOR `cutensorContract`. | [cuTENSOR API](https://docs.nvidia.com/cuda/cutensor/latest/api/cutensor.html) |
| Where does the C ABI live? | **Decided:** each part owns an `rlib` C ABI crate; only `tprims-bundle` builds `libtprims` (`cdylib` + `staticlib`) from Cargo-feature-selected parts. | Local prototype 2026-09-29 (macOS): selected parts' `#[no_mangle]` symbols exported, cross-part handle accepted. Next: CI on Linux and Windows. |
| Separate shared library per part? | Rejected. Handles, Rayon runtimes and (for static libraries) Rust std symbols would be duplicated. | Design reasoning; see [architecture](architecture.md#one-shared-library) |
| Data exchange? | **Decided: DLPack.** Operands are a borrowed `tprims_tensor` (`DLTensor*` view plus DLPack flags), built from a `DLManagedTensorVersioned` without taking ownership or from a raw `DLTensor` with caller-supplied flags; read-only outputs rejected before any write. Library-allocated outputs as `DLManagedTensorVersioned`. Conjugation as a per-operand argument. No hidden materialization. | [DLPack header](https://github.com/dmlc/dlpack/blob/main/include/dlpack/dlpack.h): the READ_ONLY flag lives in `DLManagedTensorVersioned.flags`, so a bare `DLTensor*` cannot carry it ([#2](https://github.com/tensor4all/tprims-rs/issues/2)) |
| Pool control from C? | **Decided:** create, query, budget, retain/release and close; serial and host-callback contexts as alternatives. Closing an owned pool joins worker threads kept from `spawn_handler`; closing a borrowed context only detaches. | [Rayon ThreadPool drop semantics](https://docs.rs/rayon/latest/rayon/struct.ThreadPool.html); [pool-close probe](../experiments/pool-close/README.md): the exit handler fires before TLS teardown, join does not ([#1](https://github.com/tensor4all/tprims-rs/issues/1)) |
| `f16` / `bf16` in ABI v1? | Open. DLPack has the tags; kernels do not exist yet. | Decide before the first ABI release |
| Repository placement of `tprims-exec` / `tprims-core`? | **Decided: monorepo.** strided-rs, tensorprimitives-rs and the benchmark suite are imported here with history (Phase 0); `tprims-exec`/`tprims-core` live in `crates/`. No repository-level cycle remains. | Maintainer decision, 2026-09-29 |
| strided-rs source location? | **Decided (revised 2026-09-30):** an external dependency on tensor4all/strided-rs, pinned to the v0.4.4 commit exactly as tenferro-rs pins it, so both share one `StridedView`. strided-rs itself removed its facade and einsum crates (strided-rs #282); strided benchmarks live in strided-rs-benchmark-suite. The Phase 0 import under `strided/` was removed: only `run_with_exec` had needed a strided change, and it moved to `tprims_exec::strided`. | Maintainer decisions, 2026-09-29 (import) and 2026-09-30 (revert) |
| Benchmark suite? | **Decided:** imported under `benchmarks/` as `tprims-bench`; the einsum half is frozen. Every Phase 1 implementation adds rows measured at 1T and 4T in the same run. | Maintainer decision, 2026-09-29 |
| Solves and eigendecomposition? | **Decided:** in `tprims-linalg` with the factorizations, because solves use each factorization's internal representation. Nonsymmetric `eig` is a faer wrapper in Phase 1 (tenferro exposes it); a native nonsymmetric solver is deferred. | Design reasoning; [#5](https://github.com/tensor4all/tprims-rs/issues/5) |
| Iterative Krylov solvers? | **Deferred, out of scope for now.** They need a linear-operator callback, convergence control and preconditioning, a different contract from dense linear algebra, and many consumers carry their own. A later `tprims-krylov` would depend on `tprims-blas`. | Maintainer decision, 2026-09-29 |

## Execution

| Question | Present position | Evidence or next check |
| --- | --- | --- |
| How much pool-entry cost is acceptable? | **Decided:** about 10 µs per parallel kernel is acceptable. Serial operations never enter a pool; they run on the calling thread. Parallel width is chosen from the amount of work, so full-width fan-out is reserved for large kernels. | [Rayon entry measurement](../experiments/rayon-entry/README.md), 2026-09-29, M5 Max: `install` 4 to 10 µs at 1 to 4 threads; 18-thread fan-out 55 to 200 µs. Maintainer decision, 2026-09-29. |
| Who owns the pool when a host library such as tenferro-rs also uses Rayon? | **Decided: borrow.** `tprims-exec` borrows the host's pool for the duration of a call (or a host session) and never creates a second pool beside it. `tprims_exec_rayon_create` exists only for C hosts that have no pool. **Superseded (2026-10-01):** the C host now creates it through `tprims_tapp_executor_create_rayon` and destroys it through `TAPP_destroy_executor`. | Two pools would oversubscribe cores and turn every call into a cross-pool handoff. Sharing a pool by reference requires one Rayon build in one binary. |
| Where is the pool entered? | **Decided:** inside a kernel, and only when it runs in parallel. If the calling thread is already a worker of the borrowed pool, the kernel runs in place without `install`. The caller's thread stays the driving thread for everything else, so host thread-local state needs no propagation. | Contrast: tenferro enters once per session and runs the whole session on a worker ([tenferro #1945](https://github.com/tensor4all/tenferro-rs/issues/1945)). |
| Initial backend? | **Decided (provisional):** faer for GEMM and dense linear algebra. `Par::Seq` on the calling thread for serial work; `install` on the borrowed pool, then `Par::rayon(n)`, for parallel work. Replace kernels only with measured justification. | Works with faer's ambient-pool API ([faer #319](https://codeberg.org/sarah-quinones/faer/issues/319) still open) because entry happens only at parallel kernels. |
| C ABI for execution: explicit handle per call, or a C-level "enter pool and run callback" command? | **Decided (Phase 1f; type renamed 2026-10-01 to `TAPP_executor`): explicit executor on every call**, kernel-level entry inside; small calls never enter the pool from C either. Pools created from C are owned (`Pool::owned`) and closed synchronously (workers joined, TLS-destructor handshake test). The C boundary currently costs 300-450 ns per small call (3x Rust for an 8x8 GEMM); removing per-operand metadata allocations is the follow-up. | [C ABI bench](../benchmarks/c/README.md), EPYC 7713P, `509f30f` |
| `tprims-exec` shape (Phase 1a)? | **Implemented (provisional):** `Pool<'p>` wraps a borrowed `&rayon::ThreadPool` with an SPMD mutex and entry counters; `Exec::{Serial, Rayon { pool, budget }}` with `install(k, op)` (faer-style, width one inline), `for_each_partition(k, f)` (barrier-free) and `broadcast(width, f)` (SPMD, full pool, serialized, refused when nested or wider than the pool). Host callback executors are deferred to Phase 2 with the C ABI. strided integrates through `run_with_exec` (since 2026-09-30 `tprims_exec::strided::run_with_exec`, feature `strided`; originally `strided_basic::run_with_exec`) rather than a new `ExecContext` kind, because `ExecContext` is `Copy` and lifetime-free in published strided releases. tensorcontract gains an `Spmd` seam (`Plan::run_with`) so its SPMD driver uses the host's threads; a declined broadcast reruns serially. | Phase 1a tests (width one never enters, nested/concurrent SPMD without deadlock, OS thread count constant); [exec_entry observation](../benchmarks/benchmarks/tprims/exec_entry/README.md): entry about 7 µs at width 2 to 4 on an EPYC 7713P |
| Spin-wait policy (OpenMP `KMP_BLOCKTIME` style)? | **Deferred.** Not needed while serial calls skip the pool and parallel calls are large. Revisit if a measured workload needs sub-microsecond chaining of parallel kernels. | OpenMP with active wait: 0.4 to 0.5 µs at 4 threads, but at 18 threads (all cores) a median of 59 µs and p90 of 1.1 ms after a 10 ms gap ([measurement](../experiments/rayon-entry/README.md), rerun after the [#4](https://github.com/tensor4all/tprims-rs/issues/4) fix). |
| SPMD width on a borrowed Rayon pool? | **Decided:** keep budget, active width and dispatch width distinct. SPMD kernels with barriers use `broadcast` at full pool width only; medium widths use barrier-free partitions; a partition larger than the budget is repartitioned, never served by extra threads. A subset-broadcast primitive is a separate prototype. | [Width measurement](../experiments/rayon-entry/README.md#active-width-on-a-fixed-pool): on a fixed 18-worker pool a broadcast with 1 active worker costs as much as 18 active (about 165 µs from idle) ([#3](https://github.com/tensor4all/tprims-rs/issues/3)) |

| `Strategy::Auto` for contraction? | **Decided (Phase 1e P2, 2026-09-30):** TBLIS-style when permute+GEMM would copy any operand, permute+GEMM when it fuses every operand without a copy (elementwise path for all-batch problems unchanged). On the tenferro-benchmark shape corpus (57 groups, 3150 calls; EPYC 7713P, one CCD, 3 sessions) TBLIS-style cut the calls-weighted workload time 1.42-1.47x at 1T, 1.57-1.66x at 4T and 1.70-1.87x at 8T (noise 1.7-4.7%), all of it on problems permute+GEMM must copy; on copy-free problems permute+GEMM stays faster (workload ratio 0.94 at 1T, 0.40 at 8T). The copy-aware rule beats a global TBLIS switch at 8T (about 2.35 s vs 2.60 s) and ties it at 1T. The maintainer chose it over the global switch first specified, with the decision metric changed from the unweighted geometric mean (0.93-1.09, dominated by tiny contractions) to workload time. Follow-up: optimize the TBLIS-style GEMM kernel, whose copy-free gap to faer is the remaining loss. | [P2 results](../benchmarks/benchmarks/tprims/contract/results/2026-09-30-p2/decision.txt), [contract page](../benchmarks/benchmarks/tprims/contract/README.md#phase-1e-p2-tenferro-shape-corpus-2026-09-30); `benchmarks/scripts/tblis_decision.py` |
| Batched GEMM? | **Decided:** two implementations to compare, faer plus a loop over items and the TBLIS-style kernel. **Implemented in Phase 1b** (`tprims-blas::gemm_batched`); `Auto` = faer loop, which was faster at every measured shape (TBLIS-style 10-18x slower for n <= 4, 4-11x at n = 8, 1.1-1.7x from n = 128). Next: a per-item overhead term in the batch schedule (tiny batches currently stay serial). **Confirmed in Phase 1e P2 (2026-09-30):** on the tenferro GEMM-route corpus the faer loop is 1.2x (1T) to 1.5x (8T) faster in workload time, on large synthetic batches 1.07x to 1.18x; `Auto` stays the faer loop ([P2 blas results](../benchmarks/benchmarks/tprims/blas/README.md#phase-1e-p2-batched-gemm-corpora-2026-09-30)). Follow-up: optimize the TBLIS-style GEMM engine (source study in docs/worklogs). | Maintainer decision, 2026-09-29; [Prototype 2](experiments.md#prototype-2-batched-gemm-and-factorizations); [blas observation](../benchmarks/benchmarks/tprims/blas/README.md), EPYC 7713P, `c181402` |
