phase4g/ is the experiment this run exists for (scripts/phase4g-small.sh):
speedups against `t1` **at the same size**, so the per-call fixed cost is inside
the measurement. `timed()` takes the best of `reps` with one `execute` per rep,
and threads are spawned per call.

The finding: at 64 threads, contractions below ~1 MiB run 1.2-10x SLOWER than
serial. `f32` at 0.25 MiB reads 0.10 -- a 0.22 ms contraction takes 2.2 ms. And
the optimal thread count walks monotonically with size: 4, 8, 16, 32, 64 at 0.25,
1, 4, 16, 64 MiB. A fixed default is wrong at every size but one, and wrong by an
order of magnitude at the small end (D46).

The fixed cost reads straight off the smallest rung, where parallel work is
negligible: t64 on a 0.32 ms job takes 2.29 ms, so ~2.3 ms of overhead, or ~36 us
per thread; at t8 the same arithmetic gives ~21 us. That is per-call
std::thread spawn (A43).

Two regimes, and only the first is dangerous: below ~1 MiB spawn dominates and
threading is a loss; above it the curve saturates early (best at t8-t32) because
of a bandwidth ceiling, which is benign. A guard fitted to the first must not be
fitted to the second.

phase4f/ is an ordinary thread-scaling stage on this node and is a replication,
not a new result.

Not comparable to anything measured on ccqlin038.
